# The platform seam

The play shell needs four things from the rest of Kindling. It reaches each one only through a port in [`ports.ts`](./ports.ts):

| Port | What it does | Today | When the backend lands |
| --- | --- | --- | --- |
| `SessionPort` | Who is signed in: their ID, the grade their teacher set, their locale, their avatar's look, and their class | **Stand-in.** A pretend student picked on the stand-in sign-in screen and kept in this browser's localStorage | The session endpoint, sharing the class world's session |
| `PlayRecordsPort` | Stores each play's records: its attempts, then how it ended | **Stand-in.** Kept in memory and logged to the console | The play-records endpoint |
| `LinksPort.signIn` | The sign-in page, returning to the game link afterwards | **Stand-in.** `/play/__stand-in/sign-in` | Google sign-in on the shared domain |
| `LinksPort.hub` | The class world, in front of the portal the student came through | **Stand-in.** The hubworld dev server (`VITE_HUB_URL`, default port 3001), with `?portal=&play=` | The class world's path on the shared domain |

Every stand-in lives in [`stand-ins/`](./stand-ins/), opens with a `STAND-IN` header comment, and logs a warning on start-up. Nothing outside `stand-ins/` and `src/main.tsx` imports one.

## Replacing the stand-ins

The backend is expected to be a typed Hono API like `apps/hubworld-api`: zod schemas with `@hono/zod-openapi`, an `openapi.json`, and a client generated by orval into a `packages/*-api-client`.

1. **Build the endpoints** below in the API. Their shapes are the ports' types. Write them as zod schemas in the API and keep the field names, so the adapters stay thin.
2. **Write an adapter per port** in `src/platform/` (e.g. `api/session.ts`) that wraps the generated client. Map HTTP failures onto each port's rules (see below).
3. **Run the contract suites** in [`contract.ts`](./contract.ts) against each adapter, with a harness that reads back what the API stored (e.g. against an in-memory store, the way `hubworld-api` tests its `World`). `stand-ins/stand-ins.test.ts` shows the shape.
4. **Swap the platform** in `src/main.tsx`, the only file that chooses one. Keep the stand-ins for local development without a backend, chosen by an env var, and keep using them in the shell's own tests.

## The endpoints the shell needs

Paths are suggestions. The shapes and rules are the contract.

### `GET /session` → `Student | null`

```ts
{
  id: string;          // stable, opaque; never an email or a name
  grade: number;       // 1–8, as the teacher set it
  locale: "en-CA" | "fr-CA";
  look: AvatarLook;    // from @repo/avatar; validate with its parseLook
  classId: string | null;
}
```

- Reads the session cookie the class world also uses, since there's one session on one domain.
- Signed out returns `null` (or a 401 that the adapter maps to `null`). It never redirects; the shell decides where the student goes.
- Any other failure must reject. The shell shows "try again" rather than sending a signed-in student to sign-in.

### `POST /play-records` with `PlayRecord[]` → 2xx

Every record carries:

```ts
{
  id: string;            // made by the shell; the idempotency key
  play: string;          // groups one play's records into its result
  student: string;       // must equal the session's student, or reject the batch with 403
  game: string;          // slug
  gameVersion: number;   // results keep the version they were earned under
  tier: string;
  at: string;            // ISO 8601, device clock
}
```

plus, by `kind`:

```ts
// One try at one task.
{
  kind: "attempt";
  task: string;          // the same task ID across retries of one task
  expectation: string;   // ExpectationId, edition included: "math-2020.g4.B1.5"
  succeeded: boolean;
  misconception?: string;
  assisted?: "hint" | "demonstration" | "guided";
}

// How the play ended. At most one per play, after its attempts.
{
  kind: "end";
  ending: "finished" | "left" | "crashed";
}
```

- **Idempotent by `id`.** The shell retries until it gets a 2xx, so a batch can arrive twice when a response is lost. Store each ID once and answer 2xx for duplicates.
- **In order.** Within a play, records arrive in the order they were made, so a play's `end` comes after its attempts. A batch can hold records from more than one play when leftovers are sent.
- **How a play ended is evidence.** `finished` means the game reached its end. `left` means the student chose to stop partway. `crashed` means the game broke, through no choice of the student's, so it must never count against their effort. A play with no `end` record was abandoned (the tab closed or the device died), and its `end` may still arrive later.
- **Batches hold at most 25 records.** They can arrive late: the shell keeps unsent records on the device and sends them on the student's next play, even days later. Trust `at` for when something happened, not the arrival time.
- **The adapter rejects only on failures where retrying can help:** network errors, timeouts, 5xx and 429. Those batches are retried. A 4xx means the batch will never be accepted, so the adapter logs it and resolves, and the shell doesn't retry it forever.
- Validate `game`, `gameVersion`, `tier`, `expectation` and `misconception` against the game's manifest at that version. The shell already drops attempts its manifest doesn't allow, and attempts made after a play ended.
- Scoring, results and rewards are computed from these records server-side, and are out of scope here (see ADR 0002).

### Links

- `signIn(returnTo)`: the Google sign-in entry point, which returns to `returnTo` afterwards. `returnTo` is always a path on the shared domain (e.g. `/play/plank-bridge?portal=north`). Sign-in must only redirect back to same-origin paths.
- `hub({ portal, play })`: the class world, which puts the student in front of `portal` and reveals the rewards earned by `play`. The class world needs to read these on arrival, which is work for the class world, not the shell.
