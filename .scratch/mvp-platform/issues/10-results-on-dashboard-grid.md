# 10: Plays become results on the dashboard grid

**What to build:** When a student plays, their attempts reach the API and become results. The teacher's dashboard opens on the class's students against the expectations its games evidence, with each cell showing an understanding band or "no evidence yet", next to each expectation's plain-language description.

## Comments

**2026-10-29, agent:** Done in the working tree, uncommitted.

- **Schema:** new `PlayRecord` table (migration `play_records`). Each record is stored as the shell sent it, keyed by student + record ID, with its class, game version, tier, device time (`at`), the attempt's or end's fields, and an arrival `sequence`. Records cascade from the student and the class. Results aren't stored. They're computed from the records whenever they're read, so changing a rule changes every result with no migration.
- **`POST /play-records`:** answers 200 with `{ stored }`, the number of new records. It skips IDs it already has, including repeats within one batch. It answers 403 when any record is another student's, 401 when signed out and 403 for a teacher. It refuses the whole batch with 400 for: more than 25 records; a class the student isn't in; a game or version Kindling never hosted; an unknown tier; an attempt the manifest doesn't allow; an attempt or a second end after a play's end (in the same batch or an earlier one). Nothing from a refused batch is stored. Attempts are checked by `attemptProblem` in `@repo/game-contract`, which the play shell now uses too, so both read the manifest the same way. `apps/api/src/games.ts` has `earlierManifests`: **when a game's version is bumped, its old manifest goes there**, so late records made under it still validate.
- **Play shell:** the real `apiRecords` adapter is in. It resolves on 2xx, logs and drops a batch on any 4xx except 429, and rejects on 5xx, 429 and network errors, so the outbox retries those. The play-records contract suite now takes a context (student, class, game, tier) from its harness and runs against the API. The API-client fetcher no longer throws when an error body isn't JSON, so a proxy's HTML error page still reaches the adapter as a status.
- **Scoring (`apps/api/src/scoring.ts`):** one module, with the settings in `understandingRule`. Results are grouped per student × expectation × the grade of the tier. Only the student's 5 most recent plays count, ordered by device time. A task succeeded without help needs at least one attempt that succeeded with no `assisted`; a retry that succeeds counts. Crashed plays are left out entirely, even when their `crashed` end arrives later. Bands: under 50% is "not yet showing", 50% up is "developing", and 80% up is "showing consistently". I added one rule the spec didn't ask for: "showing consistently" also needs at least 4 tasks, so a single right answer can't claim it. **These thresholds are my provisional picks; please review them with the band wording before the pilot.**
- **Dashboard:** `GET /classes/{classId}/dashboard`, for the class's teacher only (another teacher gets a 404). Columns are the expectations evidenced at the class's grades by games that are on, plus any expectation a student already has evidence for. They're sorted by grade then code, with descriptions from `@repo/curriculum`'s product layer. Students are listed by first name, then last initial. A cell takes the result at the student's grade if there is one, otherwise the latest result from another tier, marked with `otherTier` and `tierGrade`. Every result lists the games, tiers and versions it came from, for ticket 11's drill-down.
- **Teacher app:** the port has `dashboard(classId)`, a new `dashboardContract` suite runs against the fake and the API, and the fake has a copy of the understanding rule. Each class card now has a **"See results"** button that opens the grid. The grid shows the code with Kindling's description in the column header, plus each student's grade in a split class. A cell shows its band in words with a tint (it still reads in greyscale), "From the Grade N tier" when the evidence is from another tier, and a dashed "No evidence yet" when empty. A class with no students shows "No students yet". The classes screen is still the landing page: making the dashboard the landing, with a class switcher, fits ticket 12. `VITE_TEACH_PLATFORM=fake` now seeds a sample "Room 12" class (`fake/sample.ts`).
